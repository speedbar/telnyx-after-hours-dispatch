### V-025 Which call identifier is present on /dv, /mcp and /voice-events (T2.1 Step 0)
Date: 23 Nov 2026. Read from code, no changes made. Both spec test vectors checked locally with shasum: "conv-test-0001" and "00000000-0000-4000-8000-000000000001" hash to the expected first-32-hex values.
1. /dv request body: data.payload.telnyx_conversation_id (raw conversation id; dv.ts:128, today hashed to conv_hash only). The body also carries call_control_id (logged raw as call_ref, dv.ts:203) and the caller number telnyx_end_user_target (never logged raw).
2. /mcp tools/call: params._meta.telnyx_conversation_id (fallback _meta.conversation_id, mcp.ts:195-201), server-side, never from the model. The model's args.call_ref is only a fallback: resolveCallRef prefers meta (validate.ts:52-55) and always returns safeCallRef(x) = "c:" + SHA-256(x)[0:32] (validate.ts:25-37), never the raw value. V-016 observed call_ref_source=meta on every live mcp_call.
3. /voice-events: no conversation id anywhere the code reads. Identity comes from data.payload.client_state -> { c, j, t, a } (telnyx-api.ts:236-258); c is the JobActor instance name stamped from ctx.call_ref at ringrun.ts:228. payload.call_control_id on these events is the technician LEG's id, a different value from the customer-call ref.
Decision: rule 1 with one mechanism note. The conversation id is present raw at /dv and /mcp; at /voice-events its exact derivation is embedded in state.c by construction: with ref source=meta, state.c = "c:" + SHA-256(conversation_id)[0:32], so state.c minus the "c:" prefix IS the trace_id (same value, no second hash). Plan for step 1: trace_id = SHA-256hex(conversation id)[0:32] on /dv and /mcp; on /voice-events take state.c without the "c:" prefix only when it matches /^c:[0-9a-f]{32}$/; on any other ref shape (degraded "u:"-sourced, legacy) omit trace_id on that line - no id invented. This WILL match a Langfuse trace id on meta-sourced calls. The voice-side join assumes the ref came from _meta (source=meta); the args fallback exists in code, so VERIFY on the first live run after ship: one trace_id value appears on dv_in + mcp_call + voice_event for the same call. Status: READ FROM CODE.
