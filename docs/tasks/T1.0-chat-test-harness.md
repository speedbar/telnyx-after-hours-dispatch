# T1.0 Text chat test harness (branch t1-0-chat-harness)

Do this AFTER a 2-minute manual check by the human shows the chat API reaches the assistant (see "Before you start"). It is test tooling only: it changes no `src/` file.

## Why
Voice tests take minutes each and the human has to speak every line. Telnyx has an Assistant Chat API (beta) that sends text to the same assistant (`POST /v2/ai/assistants/{assistant_id}/chat`, body `content` and `conversation_id`, conversation created first with `POST /v2/ai/conversations`). The docs say server-side tools run in chat as on calls. They do NOT say whether workflow nodes, MCP tools, the `/dv` webhook or hangup behave the same in chat. This task finds out and, where it works, runs all edge-case and happy-path scenarios in one command.

## Before you start (human, not OpenCode)
The human runs the manual check and reports the result. If conversation creation or the chat call fails, stop this task and report.

## Goal
`npm run chat-test` runs every scenario in `tests/chat/scenarios.json` against the live assistant, each in its own new conversation, prints each turn, then prints PASS or FAIL per scenario and a total, and exits non-zero if any fail.

## Files you may create or change (only these)
- `scripts/chat-test.ts` (the runner)
- `scripts/chat-test-lib.ts` (pure helpers: build requests, check assertions, format output)
- `tests/chat/scenarios.json` (the scenarios)
- `tests/chat-test-lib.test.ts` (unit tests, injected fetch, no network)
- `package.json`: add the script `"chat-test": "tsx scripts/chat-test.ts"` and nothing else
- `docs/tasks/T1.0-chat-test-harness.md` (this file, only to tick done)

## Constraints
- No new dependencies. Use global `fetch`.
- Read the API key ONLY from the environment variable `TELNYX_API_KEY`. If it is missing, print "TELNYX_API_KEY is not set" and exit 2. Never print, log, write or echo the key, never put it in a file, never put it in a URL.
- Assistant id from env `TELNYX_ASSISTANT_ID`, default `assistant-14327cf7-7f6c-4fc6-b080-46739673d578` (not a secret).
- Do not print phone numbers other than the fake `0400 123 456` used in scenarios. No real data anywhere.
- One scenario at a time (no concurrency). Timeout 90 s per request. No retries on a failed request: print the status code and the error body (truncated to 300 chars) and mark the scenario ERROR.
- Unit tests make no network calls.
- STOP rule: if the first scenario fails to create a conversation (any non-2xx), print the raw status and body, do not run the rest, exit 3.

## Run flow per scenario
1. `POST https://api.telnyx.com/v2/ai/conversations` with JSON `{"name":"chat-test <scenario id>","metadata":{"assistant_id":"<id>","telnyx_conversation_channel":"web_chat"}}` and header `Authorization: Bearer <key>`. Read the conversation id from the response (accept `data.id` or `id`; if neither is present, print the keys of the response and stop).
2. For each user turn in order: `POST https://api.telnyx.com/v2/ai/assistants/<id>/chat` with `{"content":"<turn>","conversation_id":"<cid>"}`. Print `USER: ...` and `ASSISTANT: <content>`.
3. After the last turn, `GET https://api.telnyx.com/v2/ai/conversations/<cid>/messages` to read the stored messages. Confirmed by a manual check on 20 Nov 2026: the response is `{"data":[...],"meta":{...}}`; messages are NEWEST FIRST (reverse them before reading); each message has `role`, `text`, `tool_calls` (null, or an array of `{id, type, function:{name, arguments}}` where `arguments` is a JSON string, so parse it), `tool_call_id`, and `metadata`. Tool results come back as role `tool` messages. In chat, `metadata` holds only `assistant_id`: there is NO `flow_node_id`, so do not assert on nodes. Extract every tool call name and parsed arguments. If the endpoint returns 404 or an unexpected shape, print the response keys and mark tool assertions SKIPPED (not failed), and say so in the summary. The list is paged (`meta.total_pages`, `page_size` 20): follow `page_number` until all pages are read.
4. Evaluate the scenario's assertions (below). Print PASS, FAIL (with each failed assertion) or ERROR.
5. Print the conversation id so the human can open it in the Portal Conversation History.

## Assertion types (in scenarios.json)
- `reply_contains`: list of case-insensitive substrings; each must appear in the concatenated assistant replies.
- `reply_not_contains`: list of substrings that must NOT appear.
- `tools_called_exactly`: list of tool names (order ignored, duplicates counted); the set called must equal it. `[]` means no tool may be called.
- `tool_arg_contains`: `{ "tool": "create_job", "field": "address", "value": "Eleven" }`.
- `tool_arg_not_contains`: same shape, must not contain.
- `max_assistant_turns`: integer upper bound.

## Golden set rules (follow-up T1.0b, same branch, same files)
The harness is the conversation golden set. Add only these things; change nothing else.
1. Each scenario in `tests/chat/scenarios.json` gets a `golden_id` field mapping it to the edge-case/test register: E-01-cleaning=E-01, E-02-can-wait=C-09, E-04-injection=C-11, H-01-gas=C-01, H-02-flood=C-02, G-01-correction=C-05. Scenarios with no register id (E-03-abusive) get `golden_id: null`.
2. `--only <scenario id>` runs just that scenario (exit 2 style usage error if the id does not exist, listing valid ids).
3. `--repeat <n>` runs each selected scenario n times, each in a NEW conversation. A scenario passes only if ALL n runs pass. Print "k/n passed" per scenario. Default n is 1.
4. Chat replies are nondeterministic, so the gate before any prompt or workflow change is merged is `npm run chat-test -- --repeat 3` with every scenario passing.
5. Rule: every bug found gets a scenario (a new entry in scenarios.json) before the fix is accepted.
6. Unit tests (injected fetch, no network) cover: argument parsing for `--only` and `--repeat`, unknown id, the all-n-must-pass rule, and that `golden_id` is present on every scenario (null allowed).
The STOP rule (exit 3) still applies once, on the first conversation creation of the whole run, not per repeat.

## What to report back (stop after this)
1. The full run output (it contains no secrets).
2. Workflow nodes: already known to be invisible in chat (no `flow_node_id`). Say whether the replies looked like they followed the node order (address question, then name and number, then hazards) so the human can judge.
3. Whether MCP tools ran in chat (tool call names seen) and whether `call_ref` resolved (any tool failure with `invalid_input` on `call_ref`). Without a phone call there may be no `telnyx_conversation_id` in the tool `_meta`; report exactly what the tool results say.
4. Whether hangup appeared as a tool call (not expected in chat; not an assertion).
5. Anything that did not match the assumptions above, quoted from the raw response.

## Done when
- `npm test` passes (including the new unit tests) and `npx tsc --noEmit` is clean.
- `npm run chat-test` runs end to end, or stops cleanly by the STOP rule with the raw error printed.
- No `src/` file changed. The diff contains no key and no real phone number.

## Limits (write these in the README test section, do not hide them)
Text chat cannot test speech-to-text mishearing, latency, filler messages, the caller-number variable (blank in chat), real phone numbers or hangup. Voice calls stay as the final check; chat is the fast regression loop.
