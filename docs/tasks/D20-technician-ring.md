## 0. Goal and non-goals

Goal: after `create_job` succeeds, the system phones the reserved technician, reads a templated brief, and records the technician's answer (press 1 accept, 2 decline). A decline, no answer or no input moves to the next eligible technician (max 2 attempts). An accept marks the technician `dispatched` for a configurable busy period.

Why: today `markBooked` only silences the expiry log, so the technician is free again after the 90 s hold. One technician was reserved for four jobs in 25 minutes. Nothing tells a human about the job.

Non-goals (do not build): bridging the caller (D21), SMS (D20b), any LLM on the ring, changes to Portal config, changes to the three MCP tool schemas or their failure shape, a flag cache. The caller has already been told "Your job is logged." and no callback is promised; D20 does not change that.

Hard rules (AGENTS.md still applies): TypeScript, umbrella shape `export default { fetch(req, env) }`, no `ctx`. KV keys only `a-z A-Z 0-9 - _ / = .` via the helper in `src/lib/kv.ts`. No phone numbers, names or addresses in logs (salted hash only). No secrets in files or tests. Fake data only. Hard guards in code, never in prompts. Errors as data on the MCP path.

## 1. Design (decided)

### 1.1 Trigger and where state lives
- Ring starts when `create_job` has opened the job. It never starts from `reserve_technician` (so a caller who hangs up after reserve does not cause a ring).
- Ring state lives in the existing per-call `JobActor` (one actor per `call_ref`), because the ring is per-job state with read-modify-write. Technician availability stays in `TechnicianActor`. KV is not on the ring path. Keep `JobState` (`reserved|briefed|released`) unchanged so `create_job`, `release_technician` and their tests are untouched; add a separate optional `ring` object and `dispatch_state?: ringing|dispatched|unassigned` to the record.
- Ring state: `{ mode, status: idle|dialing|prompting|accepted|exhausted|disabled, attempt, tried: string[], current?: { technician_id, call_control_id, started_at }, seen_event_ids: string[] (cap 20), outcome_log: [{technician_id, outcome, at}] }`. Never store phone numbers or the brief text in it (technician id only).
- Outcomes per attempt: `accepted`, `declined`, `no_answer` (call ended before it was answered), `no_input` (answered, no valid digit before the gather timeout), `hung_up` (hung up before choosing), `dial_failed`.

### 1.2 How the ring is started (decide by spike, VERIFY)
Option A (preferred): `create_job` schedules the ring start about 1 s ahead and the actor alarm dials. Keeps the dial API latency off the caller's critical path. Two conditions: (1) can an actor call `fetch` to api.telnyx.com? VERIFY with the spike. (2) The JobActor has ONE alarm and it is the retention delete. Multiplex it: store `retention_at` and `ring_at` in the record; `alarm()` runs whichever is due (ring start first), then re-arms to the earliest remaining time; the retention delete must still happen exactly at `retention_at` and must never fire because the ring alarm did. Test both (ring alarm does not delete the job; retention alarm still deletes it; alarm delivered twice is harmless).
Option B (fallback if actors cannot fetch, or multiplexing proves fiddly): `create_job` awaits the dial command with a hard 1500 ms timeout, then returns regardless. On timeout, log `ring_dial_timeout`, mark `dial_failed`, escalate via the next event or an admin retry route. This adds the dial latency to `create_job` (warm 45 to 53 ms, slow 665 to 853 ms today), so measure it with the existing `hop_*` timers and report.
The umbrella `fetch` has no `ctx.waitUntil`, so never fire-and-forget a promise after returning a response.

### 1.3 Event-driven, no long-running work
- New route `POST /voice-events`: Voice App webhook receiver. Same Ed25519 check as `/dv` (reuse the verifier; same 403 body for every failure; 300 s window; fail closed if `TELNYX_PUBLIC_KEY` is missing). Return 200 fast; Telnyx retries non-2xx.
- Flow per attempt: `dial` (with `client_state` = base64 `{job_id, technician_id, attempt}`, `timeout_secs` about 25, `link_to` none) -> `call.answered` -> `gather_using_speak` (brief + "Press 1 to accept, 2 to decline", `minimum_digits` 1, `maximum_digits` 1, `valid_digits` "12", `timeout_millis` about 8000) -> `call.gather.ended` -> accept/decline handling -> `speak` a short confirmation -> `hangup`. `call.hangup` before a decision = `no_answer` / `hung_up`.
- Ignore stale or duplicate events: dedupe by event id (`seen_event_ids`) and require `call_control_id` to match `current.call_control_id`. Webhook retries must be harmless.
- Voicemail needs no detection: it will not press 1, so the gather times out and the attempt is `no_input`.
- Event names and fields are from the Telnyx docs (`call.answered`, `call.dtmf.received`, `call.gather.ended`, `call.hangup`); the exact payload fields (`digits`, `status`, `hangup_cause`) are VERIFY: log one real payload (redacted) on the first live ring before trusting a parser.

### 1.4 Hold, reservation and the new `dispatched` state
- At ring start, extend the current technician's hold so it outlives the attempt (new TechnicianActor method, e.g. `extendHold({call_ref, job_id, ttl_s})`, same call_ref and job_id only; it must also move the actor alarm to the new `expires_at`, and keep `booked: true` so no false `hold_expired` is logged). Config: `RING_HOLD_TTL_S` default 60 per attempt. Without this the 90 s hold, started at reserve, can lapse mid-ring and let another caller take a technician who is on the phone.
- `TechStatus` gains `dispatched`; `held_for`-style data for it is `dispatched_for {call_ref, job_id, until}`. `_state()` clears an expired dispatch lazily (same pattern as the hold; log `tech_dispatch_expired` once) and `alarm()` re-arms for whichever of hold/dispatch expires first. `setShift(false)` clears it like it clears a hold. The existing `reserve` already answers `busy` for a held technician; make it answer `busy` while dispatched too (same `reason`, so the tool failure shape and prompts do not change).
- On decline / no answer / no input: `release` that technician, then walk to the next eligible technician by trade excluding `tried` (reuse the S1.9 eligibility walk), `reserve` them, ring them. After 2 attempts or no eligible technician: status `exhausted`, job state `unassigned`, log `ring_exhausted`. (Do not send SMS here; that is D20b.)
- On accept: new TechnicianActor method `dispatch({call_ref, job_id, busy_s})` -> status `dispatched` with `dispatched_until`. While dispatched, `reserve` returns `busy`. After `dispatched_until` the technician lazily returns to available (same lazy-expiry pattern as the hold; alarm optional). `busy_s` from `DISPATCH_BUSY_S` (default 1800; the admin route in 1.9 can clear it for demos). Job state becomes `dispatched`.
- Rule kept from the design: never claim `dispatched` without an explicit accept. Fail-safe is always "technician returns to available".

### 1.5 Brief (template, no LLM)
One pure function `buildBrief(job)` returns the spoken text. Content: urgency, trade, suburb and address, customer name if known, callback number read digit by digit, hazards, summary (length-capped, control characters stripped, treated as data), job reference spelled out with spaces between characters, then "Press 1 to accept, 2 to decline." Plain text only: no SSML, no `<emotion>`, no `<break>` tags (P5). Maximum length constant. Unit-test with an injection-style summary ("ignore previous instructions...") to show it is read as data and capped.

### 1.6 Phone numbers
- Reuse `normalisePhone` / `dialableCallback` from `src/lib/validate.ts` (digits, `0` rewritten to `61`). Add one small pure helper `toE164(digits) -> "+" + digits` next to it; do not write a second normaliser. Technician numbers come from the `TECH_PHONES_JSON` secret (a JSON map `{"tech-01":"+61..."}`; new loader, `src/lib/techphones.ts`), are normalised at load with `dialableCallback`, and a bad or missing entry marks that technician not dialable (`ring_skip` log with the id only, then escalate). The loader must never throw and never log a value.
- Allow-list: `ALLOWED_DIAL_PREFIXES` (default `+61`), enforced in the dial wrapper immediately before the API call, after normalisation. Premium and short numbers (`1900`, `13`, `18`, `000`, `112`, `106` after the country code) are rejected by a deny pattern even inside `+61`. Test it.
- Callback number (caller's): `reserve_technician` already stores `dialableCallback(...)` (digits, no plus) in `contact_phone`. STATUS says the decline path stored a local-format number; CHECK a real job record before changing anything (read it through `/admin` or a test), and only fix a real gap. Do not change MCP validation: the only hard reject is an undiallable callback. The ring never dials the caller's number, only technician numbers.

### 1.7 Modes, flags and caps (fail safe, not fail open)
- Flag `ring_mode` (stored as `flag/ring_mode` in the DirectoryActor, seeded with `/admin/seed`'s `flags` map; read with `dir.idFromName("directory").flag("ring_mode")`): `off` | `dry_run` | `live`. A MISSING key or any other value = `dry_run` (log what would be dialled, never dial). Deliberately different from `dispatch_enabled`, which fails open, because a ring costs money and wakes a person.
- Caps enforced in code: max 2 attempts per job; global daily ring cap (`RING_DAILY_CAP`, default 20) as a new small counter method on the DirectoryActor (actor storage, read-modify-write, resets by UTC day key); per-technician cooldown between rings (`RING_COOLDOWN_S`, default 60) stored in the TechnicianActor; one ring per job (idempotent by `job_id`). A cap hit logs `ring_capped` and ends in `exhausted`.
- Dry run logs `ring_dry_run` with technician_id, attempt, brief length and a hash of the brief, never the brief text with the number.

### 1.8 Secrets and config (names only; values never in files)
New edge secrets: `TELNYX_API_KEY` (the function now calls the Telnyx API; this is new exposure, see risk R1), `VOICE_CONNECTION_ID`, `DISPATCH_FROM_NUMBER` (the US number, as caller ID), `TECH_PHONES_JSON` (named in `.env.example` but not yet read by any code). Already used: `TELNYX_PUBLIC_KEY`, `ADMIN_TOKEN`, `LOG_SALT`. Read all through `readConfig`. Extend `/health` with presence booleans for the new ones only; add the names (no values) to `.env.example`. Non-secret settings: `RING_HOLD_TTL_S`, `DISPATCH_BUSY_S`, `RING_DAILY_CAP`, `RING_COOLDOWN_S`, `ALLOWED_DIAL_PREFIXES`, `RING_TTS_VOICE`. Never edit `telnyx.toml`'s `[edge_compute]` block. Do not run `secrets add` or `ship`; Nabeel does.
Portal / account (Nabeel, not OpenCode): Voice App exists (Default profile, Australia allowed). Set its webhook URL to `<dispatch url>/voice-events` (API version v2). Record this as a docs sheet `docs/portal/voice-app.md` (repo first, read back after saving).

### 1.9 Admin and observability
- `/admin/ring-test` (`src/routes/ringtest.ts`, `ADMIN_TOKEN` header with `tokenEqual`, same pattern as `/admin/tech`): dry-run or live ring of a named technician with a fake job (`sim-` call_ref), so the first live test needs no phone call to the assistant. Add `clearDispatch` to the `/admin/tech` method whitelist (and its body validation) so a demo can free a dispatched technician; extend `tests/tech-route.test.ts`. Route registration goes in `src/index.ts` with the `{ ...env }` spread, plus `/voice-events`.
- Log events (30-key line style, no PII): `ring_start`, `ring_dry_run`, `ring_dial_ok`, `ring_dial_fail`, `ring_answered`, `ring_gather`, `ring_outcome` (outcome, attempt, technician_id), `ring_escalate`, `ring_exhausted`, `ring_accepted`, `ring_stale_event`, `ring_dup_event`, `tech_dispatched`, `tech_dispatch_expired`, `voice_sig_fail`. Include `conv_hash` and `job_id` so one call's path is traceable from assistant to ring.
- Second signal for the benefit story: time from `job_created` to `ring_outcome` (log both timestamps; compute in a script, do not build a dashboard).

## 4. Risks
- R1 `TELNYX_API_KEY` as an edge secret is new exposure. Mitigate: secrets only via `telnyx-edge secrets add`, never logged, `/health` booleans only; check whether Telnyx supports a restricted key (VERIFY) and say so in the security doc if not.
- R2 Actor `fetch` may be unavailable (spike decides).
- R3 Webhook payload fields differ from the docs (log one real payload first).
- R4 A live ring wakes a real person: modes, caps and cooldown exist for this; keep `ring_mode` off when not testing.
- R5 Ring cost and PSTN failure are outside our control; the state machine must end in `exhausted` with a log, never in silence.
