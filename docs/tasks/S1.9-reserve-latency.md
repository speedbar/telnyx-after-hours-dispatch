# S1.9 Reserve latency (BUG-005) (task spec for OpenCode)

Branch: `s1-9-reserve-latency`. Do exactly this task and nothing else. Run the tests, show the results, then stop. Do this AFTER S1.8 is merged and shipped.

## Why (evidence from live logs, 19 Nov 2026)
- `reserve_technician` took 1185, 1237, 1361, 1629, 911, 1251 and 1060 ms and logged `over_budget` on every call. `create_job` took 31 to 45 ms warm and about 425 ms on a cold actor. `/dv` took 530 to 650 ms.
- On a phone call every second of silence is heard. The delayed MCP filler only starts at 1500 ms, so reserve alone can eat the whole budget.
- We do not yet know which hop is slow. Measure first, then change the smallest thing.

## Rules
- Only touch the files listed. No new dependencies. Never log argument values, names, addresses or phone numbers.
- Behaviour must not change: same results, same failure shapes, same idempotency by `call_ref`. All existing tests must still pass (update only tests that assert timing or call counts, and say which).
- Do not change the Portal, the workflow, the tool schemas or descriptions.

## Changes

### 1. Instrument (`src/tools/reserve_technician.ts`, `src/lib/log.ts`, `src/routes/mcp.ts`)
- Time each await in `reserve_technician` with `Date.now()` differences: `flag`, `job_get`, `tech_reserve` (sum across attempts), `job_open`, and the total. Add optional numeric fields to `LogFields` (for example `hop_flag_ms`, `hop_job_get_ms`, `hop_tech_ms`, `hop_job_open_ms`) and put them on the existing `mcp_call` line for this tool. Numbers only.
- Do the same for `create_job` (`job_get`, `tech_status`, `brief`).

### 2. Report before changing (no file output needed in the repo)
- After shipping the instrumentation to a branch build and running three live calls, the human will paste the logs. Until then, stop after step 1 and say "instrumentation ready, waiting for logs". Do not guess at the slow hop.

### 3. Candidate optimisations (apply ONLY the ones the numbers justify, one at a time, each with its own commit)
- Cache the `dispatch_enabled` flag in module memory with a 15 second TTL (`FLAG_CACHE_TTL_S`, default 15, accept 0 to 60; 0 disables). Document in the decision log that the kill switch can take up to the TTL to apply.
- Start the first eligible `tech.reserve` in parallel with `jobs.get`; if the replay path then finds an existing job with a different technician, release the stray hold. Only do this if the numbers show the two hops are sequential and each is over 250 ms.
- If a hop is dominated by actor cold start, say so and propose a warm-up (do not build it).

### 4. Decision log and bug journal (`docs/decisions.md`, `docs/bug-journal.md`)
- Update BUG-005 with the measured per-hop numbers (before and after), the root cause, the fix, and "Signal: `over_budget` in the logs, found in every live call". Append D20 to `docs/decisions.md` only if a trade-off was made (for example the flag cache).
- Target: `reserve_technician` p50 under 800 ms on a warm path. If the target is not reachable, say what the floor is and why.
