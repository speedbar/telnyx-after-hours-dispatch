# S1.9 Reserve latency (BUG-005) and log correlation (task spec for OpenCode)

Branch: `s1-9-reserve-latency`. Do exactly this task and nothing else. Run the tests, show the results, then stop. Do this AFTER S1.8 is merged and shipped.

## Why (evidence from live logs, 19 Nov 2026)
- `reserve_technician` took 1185, 1237, 1361, 1629, 911, 1251 and 1060 ms and logged `over_budget` on every call. `create_job` took 31 to 45 ms warm and about 425 ms on a cold actor. `/dv` took 530 to 650 ms.
- On a phone call every second of silence is heard. The delayed MCP filler only starts at 1500 ms, so reserve alone can eat the whole budget.
- We do not yet know which hop is slow. Measure first, then change the smallest thing.
- Live call JAPJ3S (20 Nov 2026, S1.8 build, first call on S1.8): `reserve_technician` 1230 ms `over_budget`, `create_job` 49 ms, `/dv` lookup 680 ms. Reserve is over budget on all three live calls so far (1633, 1080, 1230 ms server-side).
- Same call, log gaps found: `technician_id` is null on every reserve line, so the logs cannot name tech-01 (only `eligible_count` 1 hints at it); `urgency_raised` records no from/to values (the transcript showed the model sent `urgent` for gas, the log cannot prove it); `urgency_raised` and `reserve_attempt` have `request_id` null while `mcp_call` has one; `/dv` lines carry `call_ref` `v3:...` and MCP lines `c:[redacted]`, so one call cannot be joined across routes; no `hold_expired` line exists anywhere, so a lapsed hold is not evidenced live.

### 2. Report before changing (no file output needed in the repo)
- After shipping the instrumentation to a branch build and running three live calls, the human will paste the logs. Until then, stop after step 1 and say "instrumentation ready, waiting for logs". Do not guess at the slow hop.

### 3. Candidate optimisations (apply ONLY the ones the numbers justify, one at a time, each with its own commit)
- Cache the `dispatch_enabled` flag in module memory with a 15 second TTL (`FLAG_CACHE_TTL_S`, default 15, accept 0 to 60; 0 disables). Document in the decision log that the kill switch can take up to the TTL to apply.
- Start the first eligible `tech.reserve` in parallel with `jobs.get`; if the replay path then finds an existing job with a different technician, release the stray hold. Only do this if the numbers show the two hops are sequential and each is over 250 ms.
- If a hop is dominated by actor cold start, say so and propose a warm-up (do not build it).

### 4. Decision log and bug journal (`docs/decisions.md`, `docs/bug-journal.md`)

Append D21 to `docs/decisions.md` only if a trade-off was made (for example the flag cache). Do NOT use D20: it is reserved for the technician ring (separate task, built after S1.9).
- Target: `reserve_technician` p50 under 800 ms on a warm path. If the target is not reachable, say what the floor is and why.

### 5. Log fixes (do these in the same task, one commit, independent of the latency numbers)
Files: `src/lib/log.ts`, `src/tools/reserve_technician.ts`, `src/tools/create_job.ts`, `src/routes/mcp.ts`, `src/routes/dv.ts`, plus the technician actor file for item (e). Name the actor file in your first message after finding it with a search; do not touch any other file.
- (a) `technician_id`: set it on the `reserve_attempt` line for each attempt and on the final `mcp_call` line for `reserve_technician` (the id of the technician that was reserved; null only when none was). Also on the `create_job` `mcp_call` line when the job has a technician. IDs only (for example tech-01), no names.
- (b) `urgency_raised`: add `urgency_from` and `urgency_to` (the enum values only) and `floor_reason` (a short category such as gas, flood, water, never the caller's words). Add them as optional numeric/enum string fields on `LogFields`. Never log the summary text.
- (c) One `request_id` for every log line produced by one tool call (`urgency_raised`, `reserve_attempt`, `mcp_call` all share it). Today the first two have null.
- (d) Correlation: add `conv_hash` to `LogFields`: 12 lowercase hex characters, a salted hash of the Telnyx conversation id (the same salt and method as `caller_hash`), null when there is no id. Put it on every `dv_*` line (the `/dv` payload carries `telnyx_conversation_id`) and on every MCP line (it arrives in `_meta.telnyx_conversation_id`). The raw id is never logged. Keep `call_ref` as it is.
- (e) `hold_expired`: when the TechnicianActor alarm releases a lapsed hold, emit one `hold_expired` line with `technician_id` and the hold length in `latency_ms`. VERIFY first that the actor can log; if it cannot, say so and stop for this item, do not invent a workaround.
- The log format has a fixed key list and a test asserts it (currently exactly 20 keys, in order). Update that test to the new key list and state the new count in your report.
