# T1.0c Chat harness checks (branch t1-0-chat-harness, follow-up to T1.0 and T1.0b)

Test tooling only. It changes no `src/` file. Do this before T1.0d.

## Why
The first live run (20 Nov 2026, `--repeat 3`) showed the harness passes scenarios the caller would have heard fail, and hides the cause of failures:
- In chat, Telnyx sends no call reference with tool calls. Every `reserve_technician` and `create_job` came back `{"ok": false, "reason": "invalid_input", "next": "fallback", "retry": false, "bad_fields": ["call_ref"]}` (server log: `call_ref_source: "none"`). So chat can never test the success path. It CAN test what the assistant does after a failure, the order of its tool calls, and the arguments of the first call.
- G-01 passed 3/3 although the assistant called `create_job` after `reserve_technician` failed and then said "Your job is logged". Only tool names were checked.
- H-01 run 1 called `reserve_technician` in the same message that asked "is that number correct?" (reserved before the caller confirmed).
- H-01 run 3 failed "hazards missing gas" almost certainly because the model wrote "Gas smell reported." and tool-arg matching was case-sensitive.
- The tool list is printed newest first, and the stored message that really carries the node is `metadata.active_flow_node_id` (seen as "close"), not `flow_node_id`.
- Scripted user turns kept going after the assistant had said Goodbye.

## Goal
Make a scenario PASS only when the assistant behaved correctly given what the tools returned, and print enough evidence to see why when it did not.

## Changes

### 1. Matching for tool-arg assertions
`tool_arg_contains` and `tool_arg_not_contains` become case-insensitive with token boundaries: the value must not be preceded or followed by a letter or digit. Required behaviour (unit tests):
- "gas" matches "Gas smell reported."
- "11" matches "11 King Street" and does not match "111 King Street".
- "0400" matches "0400 123 456".
- "Leven King" does NOT match "Eleven King Street" and DOES match "Leven King Street".
Reply assertions stay as they are (case-insensitive substring).

### 2. Chronological order and tool results
The messages endpoint returns newest first. Reverse once, so every derived list (tool calls, results, assistant texts) is chronological. Pair each role `tool` message with its call by `tool_call_id`; its `text` is JSON (an array with one object, or an object): parse it and keep `ok`, `reason`, `next`, `bad_fields` (anything else stays raw, truncated to 150 characters).
Also read the node id from `metadata.active_flow_node_id` (as well as the old keys).

### 3. Print the evidence for every run
After "tools called:", print one line per call in order:
`  1. reserve_technician {args JSON, max 300 chars} -> ok:false reason:invalid_input bad_fields:call_ref`
If any result has `call_ref` in `bad_fields`, print once per run:
`NOTE: chat sends no call reference, so tool calls are rejected here. The success path can only be tested by voice.`

### 4. Stop at the first Goodbye
After a chat reply that contains "goodbye" (case-insensitive), do not send the remaining scripted turns. Print `(assistant ended the call; N scripted turns not sent)`. Chat has no hangup, so this stands in for it.

### 5. New assertions (add to the type and the evaluator)
In these, a "failure" is any tool result with `ok: false`, and "after the failure" means any assistant text or tool call later in the chronological list.
- `tools_called_include`: list; each tool must be called at least once.
- `tools_called_only_from`: list; no tool outside the list may be called.
- `tool_order`: list; the first calls of the listed tools (ignoring any not called) must occur in this order.
- `no_tool_with_question`: true; fails if an assistant message that has tool calls also has a "?" in its text (reserved before the caller answered).
- `no_goodbye_with_question`: true; fails if any assistant message contains both "goodbye" and "?".
- `no_tool_after_failure`: true; after a failure, the only tool call allowed is `release_technician` (catches `create_job` after `reserve_technician` failed).
- `no_success_claim_after_failure`: list of case-insensitive substrings; none may appear in assistant text after a failure.
- `failure_reply_contains`: list of case-insensitive substrings; if a failure happened, the assistant text after the first failure (joined) must contain each.
- `tool_arg_contains` entries accept an optional `"if_called": true`: skip the entry when that tool was never called.
Each failing assertion prints its name and a short detail (tool name, quoted phrase).
